# App 已有记录的离线修改

适用笔记正文、日程正文/时间、待办正文和完成状态，以及三类记录的移到最近删除、恢复。归档/恢复先保存操作意图，收到真实回执才变更列表中的删除状态；重新整理原件仍需在线。当前实现不涉及 Web/Desktop 的本机存储。归档/恢复详见[闭环合同](evidence/pajio-core-20261007/offline-record-lifecycle-contract.md)。

## 本机与网络契约

- `record-mutations:v1:<scope>` 持久保存每条记录的原始 revision、期望 patch、编辑 generation、请求状态与重试时间；scope 沿用 endpoint + tenant/account + identity 隔离。已有 `record-edit:<scope>:<record>` 保存未提交输入。
- 点击保存先事务写入本机队列，成功后才能显示“已保存在本机”；仅在提交的草稿仍与本机保存值完全一致时清掉该草稿。磁盘失败不发网络请求。
- 发送前持久化固定 attempt：UUID request_key、base revision、action、patch、generation。旧 v1 队列缺少 action 时仍解释为 edit。断网、进程重开或服务重启后仍重放完全相同的 attempt，不先读新 revision 再覆盖。
- 网络请求不持有本机 scope 锁，允许继续编辑。旧请求成功只结算自己的 generation；较新的本机修改保留，下一次使用已核对的回执 revision。未知回执不会提升 revision。
- 服务端 `life_mutation_requests` 在记录修改同一个 SQLite 事务中保存完整回执。同身份/记录/key + 同 spec 返回原回执，即使记录后来更新；同 key 的不同 revision/patch/action 返回 409。CAS 失败不消耗 key。旧客户端无 request_key 时维持原 CAS 契约。
- 原有创建 outbox、修改 outbox、快照共享本机 scope 串行合并。以记录 revision 和快照 version 防旧请求回退；快照包含同记录不代表修改回执已追上，只有 revision 不小于回执才清理回执。

## 冲突与恢复

409 保存本机 patch 和读取到的服务端版本，不自动重新提交。详情页让用户读取最新版、选择“保留我的修改并同步”或“采用最新内容”。决策核对本机 generation；过期界面不能清掉后续修改。结果未知的 attempt 即使读到最新版，也不能据此替换请求或进入冲突解决；先取回原回执。已删除记录不能由保存隐式恢复，需要用户明确恢复再核对。未提交输入在刷新或冲突时保留。

队列每身份最多 100 条；暂时网络失败按 5 秒至 5 分钟退避，6 次后要求用户重试，权限/校验错误直接显示需处理。详情页和列表显示待同步、正在同步、冲突、重试状态；我的页同步计数包含修改。切换身份后，已发请求回执只归原 scope，后续队列停止。前台 15 秒同步沿用现有策略，开发短期配对不自动发送旧队列。

## 验证与边界

回归覆盖三种记录离线重开、丢回执重放、发送中继续编辑、409 两份保留与显式解决、跨身份回调、SQLite 写入失败前不发送、草稿 CAS 清理、快照乱序、并发 flush、HTTP 请求重放。测试仅使用合成数据与临时目录。没有真实账号数据写入。真机断网/杀进程的最终交互仍应在外测候选包上验收。

本机草稿与队列会随卸载/清除应用数据消失；用户可从当前身份数据导出页带走服务端已保存的记录，未同步队列需先同步。
