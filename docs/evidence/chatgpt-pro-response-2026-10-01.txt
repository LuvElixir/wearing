2.2 必须区分三个生命周期

这是我认为比“选哪个 Agent 框架”更重要的设计。

设备生命周期可以是几年，包含电脑、手机、登录环境和本地文件。

任务生命周期可能跨几小时、几天或多次人工确认，例如开店、等审核、收回退款。

模型运行生命周期通常只是某次思考和工具执行。

因此：

运行中断不等于任务取消；任务结束不等于设备销毁；会话重置不等于账号重新开通。

第一版就应保留稳定的 resource_id、task_id，再把各框架的 session_id / run_id 作为具体运行引用。不要让业务任务的存在依赖某一个聊天窗口还活着。

2.3 最小自建范围

我建议 Wearing 真正自己做的部分只有四块：

资源配方。 记录怎么取得、准备、连接、维护和退出某项资源，并逐步把可靠步骤脚本化。

任务与结果账本。 保存目标、授权、运行引用、实际动作、证据和未解决事项，而不是复制 Hermes 全部聊天数据库。

执行协调。 处理设备占用、预算、取消、接管、重试边界和故障分类。

面向你的工作界面。 让你通过对话、结果和少量决策卡控制系统，而不是经常进入远程桌面。

不建议起步自建通用记忆框架、模型调度平台、全新多 Agent 协议、复杂权限中心或多租户系统。现阶段这些工程大概率会延迟真实能力验证。

3.2 OpenAgentCore 确实值得复用的是什么

官方架构的职责分离是清楚的：

Core 管 API、鉴权、配置快照、执行编排和持久状态。
Sandbox Provider 管计算资源的取得、观察、续期和回收。
Runtime 管环境准备、执行器及事件回执。
原生 Harness 管模型和工具循环。
Harness Adapter 把原生引擎行为翻译为统一生命周期。

它最有价值的部分，是不同执行环境、不同原生引擎的生命周期管理和可观察性，而不是一个已经理解你、维护你全部社会资源的 personal agent。

这里有两个容易误解的地方。

一是，“支持 macOS”不等于支持你这台 Mac。 你的 MacBook Air 芯片尚未确认；若是 Intel，当前列出的 macOS arm64 原生安装包就不能直接当作可用路线。

二是，能力组合限制属于 OpenAgentCore 当前公共接口及其资格矩阵。 不能把它扩大成“原生模型或所有内部工具都没有这个能力”，但也不能假装公共接口已经能完成任意组合。

3.3 Hermes 比上一轮讨论时更接近可直接利用的核心

本轮源码中，Hermes 已提供三类程序化接入：ACP、TUI Gateway JSON-RPC，以及 HTTP/SSE API。HTTP 路径包含：

纯文本
启动运行       POST /v1/runs
读取状态       GET  /v1/runs/{id}
订阅事件       GET  /v1/runs/{id}/events
响应审批       POST /v1/runs/{id}/approval
注入修正       POST /v1/runs/{id}/steer
停止运行       POST /v1/runs/{id}/stop
查询能力       GET  /v1/capabilities

因此，Wearing 不需要为了做自己的界面，先重写 Hermes 的主循环。

但现成接口不替代业务账本。官方文档区分得很清楚：例如 steer 接受成功意味着内容已排队，不保证已经被模型消费；运行的 completed 表示该轮给出了最终答复，也不等于外部事务已经被核验。

电脑控制方面，当前源码把已登录浏览器工作放在 browser 工具路径，而不是让 computer_use 无差别控制一切；桌面控制另有 standard / bounded / unrestricted 模式，bounded 依赖预先审阅的能力清单。这一点应以当前版本为准，不能沿用旧文档中关于浏览器配置授权的说法。

3.4 四种组合，我的推荐顺序

以下适配负担是设计判断，不是实测工期。

方案	适合什么	重复或新增负担	我的结论
A：Hermes 为核心，接设备与服务工具	一个长期个人 Agent，逐步扩展真实执行能力	补资源生命周期、结果核验、接管协调	首选验证路径
C：OpenAgentCore＋现成原生引擎，暂不接 Hermes	先验证多引擎和远程执行基础设施	个人记忆、长期目标、事件工作仍要明确由谁负责	有价值的对照组
D：Hermes 为主，按需委托 OpenAgentCore 的限定任务	确有远程执行、独立环境或原生编码引擎需求	多一层任务映射与结果回传，但可限制在局部	有明确需求后采用
B：OpenAgentCore＋原生 Hermes 适配器	需要把 Hermes 纳入 OAC 完整执行协议和统一管理	原生生命周期适配、权限与恢复语义、打包及版本维护	保留，不建议第一步投入
为什么不直接选 B

因为它并不是“两个好项目放在一起，就自动更强”。

Hermes 自己已经有会话、工具循环、子任务、记忆、定时与接入协议；OpenAgentCore 也管理会话执行、调度、取消和持久记录。组合之后，最难的不是把一次提示词发过去，而是说清楚谁拥有尚未完成的工作。

例如：

“停止任务”由 OAC 返回成功时，Hermes 的子任务是否真的停了？
连接断开后，原任务是否仍在操作浏览器？
恢复时是继续原会话，还是无意中又执行了一次付款？
Hermes 创建的定时任务，应由哪个进程长期运行？

这些都不是 MCP 能自动解决的问题。

若以后采用 B，适配器至少要完成什么

OpenAgentCore 官方要求的不只是 run(prompt)：还包括执行器准备与关闭、精确取消、输入回执、完成确认、原生历史恢复、扩展能力声明及验收。

针对 Hermes，至少要落实：

适配项目	必须回答的问题
配置与启动	模型、工具、工作目录、Hermes profile 如何固定？
会话映射	一个 OAC Session 对应哪个 Hermes 会话？是否存在多个写入者？
事件转换	文本、工具、审批、文件、错误如何映射？
取消与完成	是“已发送停止请求”，还是所有相关工作确实停止？
恢复	断线、进程重启后怎样继续原任务，而不是重新开始？
凭据与权限	谁持有工具凭据？哪层拒绝操作？
后台工作	Hermes cron 和子任务是否允许越过 OAC 的运行生命周期？
费用	无法观测的费用怎样保留为未知，而不是填零？
发行与验收	依赖、平台、版本矩阵及失败测试由谁维护？

Hermes 的 ACP 或 HTTP 接口可以降低通信适配难度，但不能自动满足 OAC 的全部原生回执与恢复义务。

什么时候才值得上 OAC

我的采用条件是：在同一套任务上，OAC 明显减少了远程环境管理、运行恢复、原生引擎切换或产物管理的维护工作，而且没有让关键工具组合受到不可接受的限制。

在此之前，Hermes 的现有本地、SSH 等执行后端已经应当先被验证。OpenClaw 则可以作为另一种主 Agent 方案或远程节点设计参考，不建议把 Hermes、OpenClaw、OAC 都放在总调度位置。OpenClaw 本身已经有 Gateway 与远程节点分工，再叠一套同职责系统需要具体收益。

四、电脑、浏览器、手机应该怎样协同
4.1 不固定“API 优先”，固定“完成成本与可靠性优先”

我建议采用如下执行选择，而不是写死一种技术路线：

路径	适合的任务	需要重点测量
业务 API / CLI	可结构化查询、可准确标识对象、可读取结果的操作	资格、权限、限额、接口维护及结果语义
浏览器结构化控制	网页表单、后台操作、附件下载上传	登录延续、元素定位、弹窗、下载和最终保存
桌面 Computer Use	原生软件、系统对话框、跨软件操作	权限、桌面会话、锁屏、截图、焦点及接管
手机视觉控制	App 特有流程、结构树不足或界面变化较大的场景	每步延迟、截图成本、步骤数、误点和失败识别
已验证的固定自动化流程	重复且稳定的业务步骤	页面改版检测、版本兼容、异常退出
人工接管	本人认证、不可观察页面、资格确认、结果不明的高影响动作	接管上下文是否完整，恢复后是否会重复操作

我的判断是：一条成熟流程很可能是混合的。

例如，Agent 可以通过 API 拉取订单，用浏览器处理后台设置，通过手机完成某个 App 的授权，最后再用订单接口或账单核验。没有必要把整条流程统一为截图点击。

每个核验成功任务的总成本

模型费用＋设备/服务费用＋重试费用＋人工干预＋维护摊销
核验成功的任务数

核验成功的任务数

	​


模型花费和业务花费要分账。一次研究消耗的模型费用，不应与它申请的广告预算混在一起。

4.2 闲置 Mac 是首个执行资源，不是架构中心

建议先把这台 Mac 看作一个可替换的 desktop resource。

主 Agent 可以先在它上面运行以减少变量，后续再移到常驻服务；浏览器、文件、桌面应用仍可留在 Mac。Hermes 当前桌面控制文档也明确区分 Agent 所在后端、实际被控制的屏幕和客户端界面。

首轮要检查的不是“有没有成功安装”，而是：

芯片和系统是否支持；必要权限由谁授予；电脑睡眠、锁屏、断网、重启后是什么状态；远程控制是否仍可连接；Agent 是否能恢复正确浏览器配置。

建议使用专门的系统账号和工作目录，先少量授权业务账号，不把你的全部日常电脑环境直接交给一个无边界执行进程。首次授权、系统权限和恢复解锁应明确记为人工步骤。

对于租用资源，Mac/Windows 都可继续探索，但不能把“海外服务器上装一个系统”当成完全等价。以 AWS EC2 Mac 为例，它采用专用宿主机，并有最低 24 小时宿主机分配约束，并非普通按几分钟随用随开的廉价桌面容器。
AWS 文档

4.3 手机控制：我建议先比较两条，而不是全装

路线一：Hermes → Mobile MCP → 手机。

Mobile MCP 提供手机操作工具，以可访问性结构为主要路径，并可使用截图或坐标操作。它更接近“主 Agent 的一组手”，不一定需要再启动一个独立规划者。
GitHub

路线二：Hermes → Wearing 手机任务适配器 → Open-AutoGLM → 手机。

把一个明确、有限的手机子任务交给 AutoGLM，让它独立处理若干屏幕步骤，再返回证据。

两条路线应在同一批目标 App 上比较。结构化工具足够时，未必需要额外视觉规划循环；视觉路线显著减少脆弱定位和维护时，就接受它的额外费用。

Appium 适合把已经稳定的流程做成可重复自动化；Android 的 UiAutomator2 和 iOS 的 XCUITest 是不同驱动路线。scrcpy 主要用于 Android 画面查看和人工控制，不是任务规划引擎。它们应各司其职，而非一起堆成多层 Agent。
Appium
+1

4.4 Open-AutoGLM 的实际接入边界

官方 Android 路径依赖 ADB、设备调试授权和输入配置，README 给出的基础设备要求为 Android 7.0 及以上；模型可通过服务调用，也可以自行部署。它另有适合多语言界面的模型版本。因此无实体 SIM 不会阻止 App 控制验证，首轮也没有必要先在闲置 Mac 上本地跑视觉大模型。

但关键源码暴露出三个必须补齐的问题：

第一，finish 不是业务核验。
动作处理器会把 finish 返回为成功；主循环中某些解析或执行异常也可能进入结束路径。因此，“程序正常结束”不应直接映射为 Wearing 的 verified。

第二，现有敏感操作确认不是完整权限系统。
当前点击处理逻辑在动作带有特定 message 字段时调用确认回调。不能由此推断每次支付、发送或删除都会被可靠拦截。

第三，人工接管和部分动作还需要宿主整合。
源码提供了回调入口，但 Wearing 必须把它接到真实的暂停、通知、远程界面和恢复机制。部分动作处理还只是占位实现，不能按名字当作完整能力使用。

所以手机适配器应返回自己的规范化结果：

纯文本
verified        已按约定证据核验
completed_unverified  执行器宣称完成，但证据不足
needs_user      需要本人认证、选择或接管
device_offline  设备不可用
failed          明确失败
ambiguous       可能已发生外部动作，不能盲目重试
主 Agent 怎样委托手机任务

委托内容必须包含：设备、账号、具体目标、前置条件、允许动作、禁止动作、步骤与费用上限、完成证据、接管条件。

例如：

在指定手机、指定店铺账号里查看待处理订单，将订单编号与状态返回。可以搜索和打开详情；不允许发货、退款或修改价格。超过限定步骤、出现登录验证或无法确认账号时停止。

不应是：

去手机上把我的店铺经营好。

主 Agent 决定目标，手机执行器解决局部界面问题；它不能自行扩大经营范围。

动作约束必须发生在执行前

Open-AutoGLM 的 step() 本身会执行动作。因此，仅在 step() 返回后检查结果，拦不住已经发生的点击。需要在动作执行入口做前置检查、设备租约检查和必要确认。

同时要承认：截图识别加规则拦截，不足以对任意 App 提供绝对的支付安全保证。 对高影响操作，仍应结合低余额或额度限制、平台权限、确认步骤和必要人工接管；不能在另一条路径上同时给 Agent 无限制的 Shell 或凭据读取权限，又宣称入口审批不可绕过。

4.5 接管不是“打开远程桌面”这么简单

建议固定一个流程：

暂停新动作 → 撤销当前执行权 → 展示最后状态和已发生动作 → 用户接管 → 重新观察 → 核对实际状态 → 恢复。

同一手机或浏览器配置应只有一个写入控制者。用户接管以后，旧任务即使晚到一个响应，也不能继续点击。可用设备占用令牌及递增版本实现，不必另造复杂调度平台。

恢复时必须重新截图、读取账号和业务状态，不能沿用几分钟前的坐标与假设。

五、资源怎样实际落地：取得、使用、核验、维护和退出

这里要明确四件不同的事：

技术上能操作，不等于用户能申请；能申请，不等于目标平台接受；平台接受，不等于可以无人值守；无人值守一次成功，也不等于可以长期持有。

下面是我建议优先研究的真实路线。

5.1 电脑、手机、网络与常驻环境
路线	取得与前提	Agent 接入	人工、核验与恢复	成本边界

公共手机测试平台不应直接作为 personal agent 的长期账号宿主。例如 AWS Device Farm 对公共设备有清理流程，也明确提醒不要输入个人 Google/Apple ID 等敏感信息；私有设备是另一类服务，需要单独核对控制和持久化条件。

我的取舍：先本地真机，不先租海外手机。 只有某项明确需求无法由本地设备满足，且托管条件确认后，再增加远程真机。这样能把设备控制问题与地区、号码、服务资格问题分开定位。

5.2 邮箱、账号、密码、MFA 与找回

首轮应优先利用你合法持有、愿意授权的邮箱，不必为了品牌叙事更换邮箱。

对网易等邮箱，先核查当前账号是否能启用收发协议、具体认证方式和授权范围；适合协议接入就用协议，不适合则用网页。对 Gmail，官方提供 IMAP/SMTP 的 OAuth 认证路线，但账号及使用环境仍需满足服务条件。
Google for Developers

建议的验收顺序：

收取一封指定邮件 → 读取附件 → 生成回复草稿 → 经授权发送 → 在已发送记录和接收端核对 → 检查退信与线程归属。

账号管理则要分开保存：

凭据、登录会话、MFA 方法、恢复方法、实际账号权限。

不能把“浏览器今天还登录着”当作账号已经可靠接入。到期或退出后，Wearing 应判断需要刷新授权、重新登录还是本人认证。

恢复根应留在用户可独立控制的路径上。不要出现“邮箱找回依赖手机号，而手机号后台找回又只依赖这个邮箱”的无备用方案；更不能把唯一恢复码只存到 Agent 正在使用的电脑里。

5.3 电话与短信：必须拆成两条路线
路线 A：给 Agent 一条可编程的语音通信链路

Twilio 等语音服务适合作为技术候选：号码接入、呼入呼出、语音管线、按键菜单及转接，可以形成不依赖当前手机插卡的通话能力。

Twilio 美区公开参考价格包括本地号码 1.15 美元/月、部分美国/加拿大呼出 0.014 美元/分钟、呼入 0.0085 美元/分钟；这不包含全部语音模型、录音、税费或其他附加费用，也不是对你个人可成功开通的保证。
Twilio

这条路线仍要验证你的注册主体、付款条件、号码购买要求和目标地区限制。技术方案有依据，用户取得资格尚未完成核验。

语音执行器的任务应包含联系对象、目的、可答复范围、不能承诺的事项、费用限制以及何时转接给你。通话结束要形成结果记录，不能只给一段摘要却没有说明对方是否明确确认。

路线 B：长期手机号与目标平台验证码

这条路线不能被 VoIP 号码直接替代。Twilio 官方文档对短码短信接收有额外条件和限制；即使号码能收短信，也不能承诺所有第三方平台接受它作为注册或验证号码。
Twilio帮助中心

Tello 暂不作为“你人在大陆即可直接完成首次激活”的确定路线。 当前官方说明要求首次激活时人在美国并连接美国蜂窝网络。
Tello.com

SoSIM 可以进入下一轮资格核验清单，但还不能写成已走通方案。 官方商城提供 eSIM 邮件下发和香港号码相关服务，列有 33 港元的新卡套餐；不同产品、使用地点和实名条件必须分别看，不能将新卡套餐价格当作长期保号成本。
SoSIM
+1

对这类候选，采购前必须得到五个明确答案：

你的真实证件和所在地能否购买、完成所需登记？
能否在大陆首次安装并激活具体套餐？
当前设备是否真正支持其 eSIM，而非仅有相关菜单？
在大陆能否持续接听电话、接收目标服务短信？
最低保号成本、失效宽限、补卡和换设备流程是什么？

当前手机不能插实体 SIM、eSIM 又未确认，不代表号码问题必须由同一台手机解决。未来可以另配一台适合承载号码的设备，或选择符合要求的托管路线；App 执行手机与号码载体可以分离。

5.4 支付、U 卡、账单与订阅

我的判断是：不要把 U 卡定为整个系统的必备前置条件。

先核验你能够以真实身份持有的支付工具，再看目标商户是否接受、是否支持循环扣款、认证和退款。中国大陆银行发行的国际卡可以作为候选类别，但本轮没有对具体银行、卡种和目标商户组合完成确认，不能直接承诺成功。

对你提到的 U 卡方向，至少有一个明确排除项：RedotPay 当前官方发卡限制列明，中国大陆居民不符合虚拟卡和实体卡条件。它不能作为你当前身份条件下的默认解决方案。
RedotPay

本轮尚未确认一条可向你承诺的“大陆本人资料、无需境外居留、可正式开通且适用于目标商户”的 U 卡完整路线。 这不等于所有产品都不可行，而是不能拿未经核实的广告宣传作为资源底座。

Wearing 的支付整合至少要保存：

环节	必须记录的事实
开通	发行主体、资格、真实账单资料、认证方式
费用	开卡、月费、充值、换汇、交易、退款或提现费用
授权	商户、单笔、累计、订阅期限和人工确认要求
扣款	是否仅授权、是否已扣款、是否结算
权益	服务是否真的开通，开在了哪个账号
维护	余额不足、卡过期、3DS、自动续费失败
退出	取消订阅、停止未来扣款、处理退款及剩余资金

最重要的失败状态是：

页面超时，但可能已扣款。

此时应先查订单、账单和权益，不能再次点击购买。给浏览器任务一个内部幂等键，并不能让外部商户自动提供“恰好付款一次”的保证。

另外，预算检查不能只是系统提示词。应结合支付工具自身限额、低余额、商户侧权限等可执行限制。对无法可靠约束的支付界面，保留最终确认，比假装完全自主更符合你的控制要求。

5.5 海外网店：开店、收款、结算必须分别验收

“能打开 Shopify 后台”只是电脑操作能力的一部分。

真正的经营依赖至少包括：

经营主体与商品资格 → 店铺账号 → 商品和履约 → 支付接入 → 结算账户 → 退款与客服 → 日常对账。

Shopify 官方支持第三方支付提供商，并要求按提供商条件验证账户；其文档也明确，添加支付提供商属于店铺所有者权限。
Shopify Help

我建议优先核验使用你真实可用的主体经营海外业务，而不是先为了“海外身份”设一个境外公司。

例如 Airwallex 官方有中国大陆公司开户资料清单，包含营业执照、授权人和最终受益人证件等材料。这说明存在可研究的大陆企业申请路径，但不意味着你提交后必然获批，更不意味着账户获批就同时获得所有发卡、收单和结算产品。
Airwallex帮助中心

具体可以拆成两条并行工作：

**软件路线：**创建测试商品、编辑页面、管理草稿、处理模拟订单、导出对账数据。

**资源路线：**确认主体、商品类别、支付提供商、结算账户、退款、物流和税务要求。

只有后者成立后，真实订单才进入完整验收。一次有效的经营验收，不是“上架成功”，而是能把一个授权测试交易从下单追踪到收款、履约或退款，并确认账目一致。

5.6 Google Ads：不需要先假设自己是海外广告主

Google 官方对中国广告主有明确的验证材料路径：组织可涉及营业执照及授权代表证件，个人则提交相应的中国政府签发证件。由此看，广告账户路线首先应从真实主体和实际账单信息出发，而不是从海外手机号或海外 IP 出发。

我建议三个层级分开：

层级	验收内容
操作能力	在测试环境或暂停状态下创建、检查、修改广告对象
真实投放资格	广告主验证、付款、网站与业务审核
日常经营能力	在已批准规则内观察、汇报、调整并核对真实效果

Google Ads 官方测试账号不产生真实广告投放及对应效果数据。因此测试账号成功不能证明真实投放、费用和转化回收成立。

浏览器操作可以先验证；后续需要批量和持续操作时，再接 API。API 的授权与准入应按实施时的官方流程和账户实际权限验证，本轮检索到的相关文档版本存在差异，不宜把旧的申请步骤写死进安装器。

策略边界应由你明确，例如：

可以更新日报、发现异常和提出建议；只有满足已批准条件，才调整指定广告系列；不能自行开新预算或更改付款方式。

5.7 ChatGPT / Claude 订阅：保留目标，但不要把资格问题误写成自动化问题

当前官方支持地区列表没有中国大陆；OpenAI 还明确提示，从不支持地区访问可能导致账户被限制。远程电脑、海外号码和支付工具本身，不能直接证明你的整体使用方式满足服务条件。

因此，这个目标目前应标记为：

自动化流程可研究，实际服务资格未成立，不能作为首个必须成功的付费验收场景。

与此同时，Wearing 本身的模型调用可以使用对你的身份和所在地实际可用的提供商或自托管端点。不要让某一个消费级订阅能否取得，决定整个 Agent 项目是否开始。

消费级订阅、开发者 API 额度和原生 Agent 引擎的认证方式也应分开管理。

5.8 投资策略执行：先建设执行能力，不预设账户已合格

这条路线至少有三层：

研究与回测；模拟执行；合格账户中的真实执行。

目前不应把“可打开券商或交易平台页面”当作开户、入金和自动化交易资格成立。本轮没有确认适用于你当前条件的完整股票或加密资产账户取得路线，因此真实交易层保持待核查。

软件层可以先明确：

用户确定	Agent 执行
策略版本、标的范围、资金和风险边界	读取数据、生成符合规则的操作计划
允许交易的账户和时段	下单前检查账户、余额、仓位和规则
停止条件与异常处理	跟踪受理、部分成交、成交、撤单和对账
何时修改策略	提交异常与结果，不自行改写策略目标

对于对时效敏感的交易，我的建议是优先使用合规可用、能精确查询订单状态的接口；图形界面用于研究、管理和补充，不应只因“能点按钮”就承担无人值守交易。 找不到足够可靠的订单状态和恢复机制时，停在模拟或人工确认层。

支付、提现与更换收款账户应与交易执行权限分离。这里不是缩小 Wearing，而是在区分“能研究一种能力”和“具备真实承担该行为的条件”。

5.9 地址、文件、社会联系与现实服务

这一组不应成为末尾的杂项。

地址要按用途建档。 通信地址、仓库、退货地址、账单地址和居住证明不是同一种资源。取得某个收件服务后，要验证它接收什么、谁能签收、如何转寄、费用怎样计算，以及停止服务前有哪些账号必须迁移。

文件先用现有存储建立连续性。 固定工作目录、版本记录、证据目录和加密备份，再按需要接云存储、域名和服务。恢复验收应是“找回指定版本并能继续任务”，不是“备份进程显示成功”。

社会联系要包含待办关系。 联系人不只是通讯录，还应包含：当前事项、等待谁回复、已作出的承诺、允许使用的渠道。外部邮件、网页和消息是待理解的信息，不能因为其中出现“请转账”就自动获得你的授权。

现实服务要有交付链。 预约、物流、采购等任务，应记录确认号、服务方、费用、地址、交付或签收及争议处理。服务方要求本人出示证件或签字时，明确转交，不把它藏在“Agent 已完成”里。

六、主动性与长期经营：从上下文产生任务，不从空闲产生任务

你的最新定义对主动性的约束是合理的：对话、已有目标和外部事件提供起点，Agent 判断是否值得做；长期方向由你决定。
wearing-pro-brief-2026-10-01

我建议把主动工作分成三种，不再增加独立的“主动性大脑”。

有限探索。
你随口提出一个想法后，Agent 根据既定授权做小范围调查。输出应包括结论、证据、投入，以及是否值得继续。它不能把“看看海外网店机会”自行升级为开店和投广告。

目标维护。
对已接受目标，检查下一步依赖、待回复、到期或异常。没有新的有效动作就等待，不为显示活跃而持续调用模型。

业务事件处理。
新邮件、订单、账单、审核结果、设备离线等进入事件队列。先去重、归属到目标，再判断通知、自动处理或等待确认。

授权应同时规定模型研究费用与外部业务费用。例如允许有限研究，不代表允许购买报告、订阅工具或联系第三方。

这部分可以复用 Hermes 的定时、记忆和工具能力，Wearing 补充的是目标关联、事件去重、预算与结果状态，而不是再造 cron 和多 Agent 系统。

七、探索路线：按依赖推进，用证据决定采用或放弃
7.1 先统一验证等级
等级	含义	不能误写成什么
L0：文档可行	官方说明或源码存在相应路径	不是可在你的设备运行
L1：资源可取得	你的资格、材料、支付和取得流程成立	不是 Agent 已会使用
L2：连接成功	已认证连接，基础读写或动作成功	不是任务完成
L3：任务完成	真实任务有独立完成证据	不是长期稳定
L4：持续稳定	跨会话、断线、到期或恢复后仍可靠	不是所有平台通用
L5：他人复现	第二个人按配方取得相同能力	不是只靠原开发者现场修补

一个能力可以处于混合状态：手机控制 L2，某 App 查询 L3，支付仍 L0；这比一个总进度百分比诚实。

7.2 第一批实验

下面的测试数量和门槛是建议的工程筛选标准，不是预测成功率或工期承诺。

实验 0：资源与版本基线

**前置条件：**无采购要求。

确认 Mac 芯片、系统、存储、网络、远程接管条件；确认手机系统、调试连接和 eSIM 状态；列出可用模型服务、拟授权账号及恢复方式。

锁定框架提交、依赖和配置，不在同一轮验收中自动升级 main。

**通过标准：**知道设备支持什么、哪些步骤必须人工、失败后如何恢复。不能确认的项目明确标记，不用默认值替代事实。

实验 1：Hermes 在现有 Mac 上完成一个完整低风险任务

任务可以是：

根据一段研究目标查找资料，形成带来源的结论，保存文件，并在后续对话中继续修订。

覆盖模型、浏览器、文件、会话、费用和结果核验。再加入一次主动中断和一次恢复。

**通过标准：**产物真实存在，来源可追溯，中断不丢已完成部分；恢复后能继续，而不是从头假装做过。

**放弃或替换条件：**目标系统不兼容、桌面权限路线无法稳定建立，或基本运行与恢复成本明显不合理。此时替换执行路径，而不是先写 OAC 适配器补救所有问题。

实验 2：A 与 C 的小规模对照

同一批任务，分别用：

A：Hermes 直接执行。
C：OAC＋一个现成、服务资格成立的原生引擎。

先不写 Hermes 原生适配器。对比文本任务、文件操作、工具调用、取消、断线、状态和产物读取。

**建议样本：**约 10 个固定任务，至少重复两轮，并加入明确失败场景。

记录成功、误报完成、人工次数、恢复步骤、总费用和开发修改量。不同模型或工具配置的差异必须注明，不能把模型差异归因于框架。

**采用 OAC 的条件：**它在执行环境和恢复管理上有可重复的实际收益。
**暂不采用的条件：**仍需要自行补同样的能力，却增加一套状态和限制。
**启动 B 的条件：**A 已跑出明确能力，而 OAC 又展示了必须纳入统一管理的收益。

实验 3：无卡手机控制与电脑—手机交接

选三个类型不同的低风险 App 流程：

读取信息；填写但不提交；跨电脑与手机转移信息并核对。

比较 Mobile MCP 与 Open-AutoGLM，优先用现有设备，不先 Root。

加入设备离线、弹窗、登录过期、卡在同一页面、人工接管。对英文界面单独评估，不能用中文 App 成绩代替。

**通过标准：**任务返回证据，无法完成时正确分类；接管后没有旧任务继续点击。

**采用标准：**按目标 App 分配执行路线，不追求一个手机控制器覆盖全部。

实验 4：邮箱与电话号码的实际通信

邮箱先做完整收发和附件流程。电话只在资源取得条件成立后，验证与你或已同意测试的对象通话、按键菜单、转接和结果记录。

长期号码另外验证普通 SMS 与目标平台验证码，并记录保号和换机要求。

**通过标准：**消息或通话真实到达，身份和对象没有混淆；失败可诊断，号码不是一次性可用。

这一步可以与前面软件实验并行，不必等待整个号码链路完成。

实验 5：一个资格成立的低额经济闭环

未来另行授权后，选择一个真实可用的服务验证：

选择方案 → 确认账号与价格 → 付款 → 核对权益与账单 → 取消续费 → 核对未来扣费状态。

不是必须选择 ChatGPT、Claude 或某张 U 卡。

**通过标准：**钱、账号、权益和账单一致；网络中断或页面超时不会引起重复购买。

**停止条件：**资格不成立、费用不透明、无法核对扣款状态，或者执行权限无法约束。

实验 6：三个方向的长期任务，而不是一个垂直 MVP

同时保留：

**店铺：**商品、草稿、订单与客服工作。
**广告：**测试或暂停对象、数据核对、规则化建议。
**投资：**已确定策略的模拟执行与对账。

每个方向都有独立的真实上线门槛；没有资格的方向停在模拟，不影响其他方向进入真实任务。

这能检验 Wearing 是否是一个通用个人行动环境，而不是只在单个演示上表现良好。

实验 7：持续运行、故障注入和第二人复现

进行一段连续运行观察，例如先覆盖 7 天，再覆盖真实的续费或过期周期。

主动测试：模型超时、设备重启、网络恢复、会话退出、额度不足、权限撤回、页面变化、用户接管、恢复到另一台设备。

最后让第二位开发者仅凭配方和自己的资源复现，不依赖你的真实凭据。

**通过标准：**明确恢复过程、保留证据、不重复产生外部动作；无法恢复时能准确说明人工需要做什么。

7.3 我会用什么指标，而不是“接入了多少工具”
指标	意义
核验成功任务比例	真正办成了多少，不是模型报告完成多少
错误报告完成次数	尤其关注“其实没成功却说成功”
每个成功任务总成本	包含失败尝试、人工和维护
不必要人工干预次数	距离“平时不用自己进电脑”还有多远
未知结果后的重复动作	是否出现重复购买、提交、发信或下单
恢复后继续推进比例	持久性是否真实
配方复现成功率	能否把个人经验变成软件能力

低风险流程可以先把“20 次中至少 18 次独立核验成功”作为筛选目标，但这只是小样本筛选，不足以证明生产稳定性。高影响动作更重要的门槛是：不越权、不错误报告成功、结果不明时不盲目重试。

八、最终应该沉淀成什么软件

我认为 Wearing 最有价值的沉淀单位不是一个新 Agent，也不是一个泛泛的 Skill，而是一个经过验证的资源—任务配方。

例如：

“在某类 Mac 上，为个人 Agent 建立持久浏览器工作环境，并在登录失效和重启后恢复。”

这份配方应同时包含：

部分	内容
适用范围	身份、地区、系统、设备、服务版本
前提检测	自动检查什么，哪些必须人工确认
取得与安装	官方渠道、材料、配置及成本
执行方法	API、浏览器、电脑或手机路线
验收	输入、预期结果、独立证据
维护	续费、更新、健康检查、会话失效
恢复	中断点、补救、接管与迁移
退出	停止任务、撤销权限、解绑和数据清理
已知限制	哪些只经文档核对，哪些做过真实测试
复现记录	日期、版本、设备、费用、失败情况

早期可以是一组目录、配置文件、测试和少量连接器。等多条路线出现真正重复的结构，再提炼为软件界面和通用能力。先让抽象从真实重复中长出来，不先为一个想象中的完整世界造框架。

最终判断

Wearing 的探索范围应该保持现在这么宽，但第一阶段的技术组合应尽量简单：

Hermes 负责持续理解和推进；电脑、手机及服务执行器负责实际动作；Wearing 负责把资源取得、任务证据、约束、维护和恢复接成完整过程。

OpenAgentCore 不是不合适，而是需要先证明它对这套过程的增益。 先用现成引擎做对照，比立刻投入 Hermes 原生适配更有信息价值。手机方面，Open-AutoGLM 有实际复用价值，但要把“能操作屏幕”升级为“有界委托、可核验、可恢复的手机工作能力”。

当前最大的未决项仍然是：你的具体 Mac/手机能力、适用号码的实际取得、可用支付工具，以及部分目标服务的资格。它们应成为独立验证任务，而不是被包装成已经解决，也不应让整个软件探索停下来。

这个项目真正值得追求的成果，是逐步证明：一个由你控制的 Agent，不仅能调用工具，还能长期维护自己的工作条件，在真实社会流程里把事情办完，并把这套能力交给另一个人复现。
