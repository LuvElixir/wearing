# Pajio 真实核心服务部署验收

2026-10-09，完成公网入口、真实身份服务、控制数据库和两个独立租户执行环境的部署。本轮结论是**真实服务可进行受控测试**，不是整个产品已具备不受限公开运营条件。

## 已生效的服务

- 产品入口：`https://pajio.luckyloading.com`。身份服务：`https://id.pajio.luckyloading.com/realms/pajio`。
- 公司公网网关经专用 WireGuard 应用通道及双向 TLS 到达控制 VM；控制 VM 再经双向 TLS 与每实例 Bearer 访问两个独立 KVM 租户。管理隧道保持独立。
- 控制服务、PostgreSQL 16、Keycloak 26.7.4 和租户 worker 均已运行并启用开机启动。主服务使用 Ubuntu Python 3.12，Hermes 使用自身固定的 Python 3.14 环境。
- Keycloak 为生产模式，启用授权码 + PKCE；注册关闭，只有已登记 membership 的验收账号可进入。临时 bootstrap 管理员已删除，永久操作者下次交互登录要求设置 MFA。尚未配置 SMTP 找回密码。
- 两个租户配置真实 DeepSeek `deepseek-flash`；只传输了该模型凭据，没有复制开发机的历史会话、记忆或其他服务凭据。
- App 源码的默认服务地址已指向上述 HTTPS 入口；本轮没有声称重新签名、分发或在实体 iPhone 上完成新版安装。

安装产物：`wearing-0.2.0-py3-none-any.whl`，SHA-256 `c69d66b4ad1aed6357ee563efde4c4666b0d9af590e0fc7d4d6e51969de29457`；固定依赖清单 SHA-256 `eaf7aff142f7b272f6853e51ff512e74ddeee06d6044512fd77a5613ccc0f2a8`。Hermes 源归档及运行工具均通过固定散列校验。

## 实际验收

| 项目 | 观察到的结果 |
| --- | --- |
| 真实登录 | 两个账号经公网 Keycloak 登录后，产品页与账户会话均返回 200，并进入各自租户 |
| App 登录交接 | 固定 `pajio://auth` 回调的一次性登录码：正确 verifier 换取会话 200；错误 verifier 与重复使用均 400 |
| 真实工具任务 | A 创建 `pajio-core-acceptance.txt`，调用工具读回；再通过公网文件 API 独立下载，随机验收标记逐字相同 |
| 独立模型任务 | B 返回 `173 × 29 = 5017`；A/B 任务均正常结束，产品保留“结果已返回、待用户验收”的状态 |
| 重复提交 | 相同 request_id 返回同一 task_id，没有生成第二个任务 |
| 账号隔离 | B 查看 A 的任务与文件均 404；伪造 tenant 请求头仍为 404；B 的对话不含 A 的验收标记 |
| 网络隔离 | 控制 VM 可连接租户的服务端口；两租户不能互访，不能连接控制 SSH、宿主管理端口或元数据地址；模型公网接口可达 |
| 管理边界 | 匿名产品 API 为 401；公网内部接口、Keycloak admin 与 master realm 为 404；没有客户端证书的内部 TLS 请求被拒绝 |
| 重启恢复 | 重启控制网关和两租户 worker，原 App 会话仍可用，任务输出与文件保留，两个引擎重新 reachable |
| 最终探测 | 重启及备份后，两租户共 6 次公网状态请求全部 200/reachable，耗时 55–112 ms；只是状态接口样本，不是任务延迟或容量基准 |

真实任务共观察到 5 次模型请求：A 4 次，输入 68,069 / 输出 592 token，其中缓存读取 50,688 token；B 1 次，输入 16,472 / 输出 44 token。平台账本与任务 token 回执一致，无未结算请求。两个租户各设置 100 次模型调用、单并发，余量分别 96 / 99。**调用次数和 token 回执不是人民币账单，也不是已测得的每用户月成本。** 当前限额不会自动按月重置。

## 备份及恢复

控制 PostgreSQL 使用 pg_dump；租户数据归档期间停止对应 worker，归档后自动启动。使用 AES-256-GCM 加密，在 Mac 与公司云网关各保存一份密文，解密密钥仅保存在 Mac 私有部署目录。

已实际解密并校验散列；两份 PostgreSQL dump 分别恢复到新建隔离测试数据库，恢复后的业务 schema 表数与原库一致（控制库 9、身份库 100），随后删除仅本次新建的恢复库。两租户各 7 份 SQLite 数据库完整性检查通过，验收 task 行均可读回；A 的文件标记一致，B 没有该文件。

这是一轮应用数据备份与恢复验证。受管运行时缓存和可重新安装的依赖未放入应用备份；恢复仍需固定版本安装包及宿主/VM 配置。尚未建立定期异地备份、长期保留和自动恢复告警，不能把一次成功当作灾备体系完成。

## 发现并修复的问题

1. 公网代理首次返回 502：内部服务证书名称与 Nginx 校验名不匹配。补全 DNS SAN，并使用固定内部服务名校验；没有关闭 TLS 验证。
2. Linux Node.js 缺少 `libatomic.so.1`，固定工具无法通过启动校验。补装 Ubuntu `libatomic1` 后重试成功。
3. 主服务 wheel 的整个 site-packages 被插入 Hermes 搜索路径，导致 Python 3.14 加载了 Python 3.12 的 pydantic 扩展。桥接改为只加载 wearing 包，隔离宿主依赖；新增独立进程回归测试。真实引擎启动及模型调用随后通过。
4. 安装镜像下载超时并发生重试；使用经固定 SHA 校验的工具缓存完成安装。临时公开缓存仅包含官方安装包，已清理。

早期登录成功但 worker 未就绪时的 502、首次安装失败日志及最终成功记录分别保存于私有 `.wearing/on-prem/20261009/`，不覆盖失败记录。
