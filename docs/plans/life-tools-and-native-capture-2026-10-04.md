# Wearing：内置生活工具与随手记录

2026-10-04 续议。用户明确要求：日历既能读也能创建；从没有记录习惯的用户出发；客户端内置有价值、能与 Agent 协作的生活工具；多端共享数据，并利用各端原生操作。本文保留完整规划；首批本地工具已实现，实施范围见下方检查点。它更新了 [上一版规划](personal-experience-2026-10-04.md) 的首版范围。

## 实施检查点：2026-10-04

已交付今天、自有日历月/周/议程视图、待办完成/重开、短笔记、编辑、可恢复移除与原记录继续聊。FullCalendar 7.1.0 标准 MIT 组件已整合并随包提供。用户与 Agent 使用同一持久记录，按身份分隔；并发写入必须匹配版本，重复创建使用幂等键。真实模型写入、两个浏览器冲突保护、界面创建/完成/移除/恢复均已验收。

实现先采用 `event/task/note` 三种严格校验的记录，`list_name` 表示待办分组，尚不是独立清单实体。`capture/asset` 与私有媒体原件已在下一增量实现，支持本地 OCR、转写与后台整理，见 [随手输入](../capture-input.md)。离线副本、搜索、重复日程、目标关联、系统日历和通知仍属于后续范围。当前刷新同步是多个网页连接同一服务；不能等同于所有原生端已完成云端同步。详见 [实现说明](../life-tools.md)与[验收](../evidence/life-tools-2026-10-04.md)。

## 1. 产品承诺

**你可以随手说、拍、写，Wearing 会帮你记好、安排好，并在有用的时候接着处理。**

第一天没有外部日历、没有笔记、没有配置任何账号，也能得到价值。日历、清单、笔记是 Wearing 自带的可用工具，用户和 Agent 共同操作同一份内容。外部系统集成把这些工具接进已有生活习惯，不是开始使用的前提。

基本操作无需等待模型：用户直接新建日程、拖动时间、写字、勾选和搜索，立即得到本机保存反馈，在线时完成云端同步。AI 整理在后台运行；模型暂时不可用，基础工具仍然好用。

工具进入首版的判断：是否经常用；是否能独立帮用户完成一件事；Agent 是否能读写并根据变化继续行动。基础工具先收束为三组，其他生活场景组合已有对象来完成。

| 工具 | 用户直接使用 | Wearing 能帮什么 | 首版范围 |
| --- | --- | --- | --- |
| 日历 | 日/周/月与议程视图；创建、改时间、取消；重复安排；按时间查看 | 从明确表达创建安排、关联资料、发现冲突、调整已授权的安排 | 自有日历与提醒可独立使用；外部日历按来源逐个接入 |
| 待办与清单 | 快速添加、勾选、排序；购物、行李、准备事项；可选截止时间 | 从记录提取待办、补充准备清单、提醒未闭合的约定；执行可交托部分 | 无时间事项也能成立；完成、延期与归档清楚区分 |
| 备忘与收藏 | 短文本、语音、照片、链接、文件；编辑、搜索、主题集合 | 命名、摘要、归类、找回原件、与人物和目标关联 | 收藏是笔记的一种来源/视图；不新造第二套资料库 |

订阅到期、纪念日、票据保修、想去的地方、旅行准备等，分别由时间、清单与资料组合实现。地点与联系人先作为关联信息，调用系统地图/联系人承担已有能力；预算账本、邮箱、支付等另按真实需求和资源推进。

## 2. 从一件小事建立习惯

习惯来自“交给它后真的省了一次心”。首次使用直接邀请用户交代一件明天的小事，可以自己说，也可以选择示例。完成一条真实记录之后，才在具体需要时引导通知或系统日历授权。

示例第一轮：用户说“明晚八点留半小时整理照片”。Wearing 创建自有日程，返回带具体日期、20:00–20:30 的小卡片，可直接改时间或撤销。若提醒尚未启用，明确显示尚未启用并提供入口；不能仅保存日程就承诺会提醒。

下一次使用从实际记录继续：“今晚有半小时整理照片。”用户完成后可勾选，资料和进度跟随原事项。连续的成功体验形成随手交代的习惯，产品无需用户先建立完整日历体系。

### 判断一句话该放在哪里

| 输入示例 | 默认处理 | 必须保留的区别 |
| --- | --- | --- |
| “明天下午三点跟小王聊半小时，帮我记上” | 直接创建日程，显示解析后的日期、时间与时区，附撤销 | 用户已经表达创建意图，无需再问一遍是否保存 |
| “家里没洗衣液了，记一下” | 放进购物清单，已有同一未完成条目则提示并合并来源 | 不自动下单，不强行安排一个日历时间 |
| “这家咖啡店下次想来”加照片 | 保存地点笔记和原图，供以后检索 | 兴趣尚未成为预约 |
| 分享活动海报，没有附加指令 | 保存资料，提取时间地点，提供“加入日历”动作 | 海报日期不表示用户一定参加 |
| “周末找时间整理照片” | 保存待办，给出可选时间；保留未排期状态 | 不把一个模糊意向写成确定承诺 |
| “以后周五都帮我整理这周的资料” | 形成 Wearing 的持续工作约定，显示范围与频率 | Agent 自己的工作不会占用用户日历时间 |

明确的内部记录指令直接保存；一次必要的字段澄清只针对影响结果的缺项。识别有歧义的时间或人物时，先保住原内容，再就这一处澄清。默认提醒提前量、时间段和日历来源可以逐渐记成偏好，后续不重复设置。

## 3. “记一下”：统一入口，各端顺手

“记一下”为暂定动作名称，涵盖文字、语音、相机和系统分享。用户不必先判断输入应当属于哪种工具。它可独立打开，使用完即可返回原场景。

### 手机：拍一下，说一句

入口放在拇指易到的位置。点按开始语音，再点按结束；保留清晰的录音状态、取消和改字入口，不要求一直按住。相机与语音可组合：拍完补一句用途，比填写多项表单更自然。安静场合直接写字，分享外部内容时保留标题、链接和原附件。

流程：

1. **先接住。** 文字、音频和照片可靠保存在本机后，马上显示“已记下”；有网时上传租户私有存储，离线时显示“存在这台手机，联网后整理”。
2. **后台整理。** 云端转写/识图，区分记录意图与行动意图，提出标题、类型及关联。用户不必停在加载页等它结束。
3. **形成结果。** 明确指令直接生成相应记录，歧义项保留候选。以一张可编辑卡片呈现“记录了什么、放在哪里、提醒是否启用”。一份输入可以关联笔记与待办，使用相同来源，避免堆出重复副本。
4. **在需要时回来。** 日程到期、资料有新用途或原目标出现变化时再引用。用户纠正原记录后，后续整理与提醒同步更新。

仅打开相机或拍下一张照片不立即创建日程、待办或云端上传。拍摄预览中的“记下”才提交；分享面板同样有清楚的提交动作。首次使用说明云端整理范围，照片选择采用系统选取器，只接收用户选择的内容。

原音、原图与整理文本关联保存；摘要不覆盖原件。附件提供保留/删除选择，删除记录需要连带处理上传队列与衍生结果。照片上的文字属于材料，不是能扩大 Agent 权限的指令。

删除笔记会取消该笔记尚未完成的整理；已经独立创建并被用户保留的日程或清单条目不静默删除，显示关联关系供用户选择。删除某个日程则撤销它自己的提醒。原附件被多条记录引用时，按保留选择处理，避免误删其他记录仍需的资料。

### 桌面：从正在看的内容出发

全局快捷键打开小输入窗；可粘贴选中文字、拖入照片或文件，短语音同样可用。桌面擅长整理：在周视图拖动日程、批量整理笔记、勾选清单、对照原图校正识别结果。

原生拖动和直接编辑本身就是有效指令。例如用户把“整理照片”拖到周日，Wearing 应更新原记录与提醒，并能在后续对话理解这个变化，不要求再发一句话通知 Agent。

## 4. 客户端的信息结构

桌面侧栏建议直接给出 **今天 / 日历 / 清单 / 笔记**。对话是随时展开的侧面板，选中的日程、笔记或清单自动成为明确的对话上下文。用户可以只用工具，也可以在同一处让 Wearing 帮忙。

手机建议优先露出今天、日历、笔记以及“记一下”。清单在今天直接可达并能打开独立清单页；对话保持一键进入。底部导航与捕获按钮的位置通过原型验证，不为了和桌面一致而硬塞全部项目。

“今天”聚合真实日程、清单中的当前事项和 Agent 的结果；它不是另一份数据库。“笔记”保存用户原始记录与整理资料；“Wearing 记得什么”另设可查看和纠正的记忆入口，避免把用户笔记与 Agent 推断混成一篇会被自动改写的文档。

长期目标继续使用已有目标对象，关联具体清单、笔记和日程。人与 Agent 的责任要明确：Agent 完成找资料，不代表用户已经读完资料；日程过去，也不自动等于事项完成。

## 5. 一份数据，两种操作入口

Wearing 自有记录以租户私有云端数据为权威版本。各端保留可离线使用的本地副本；界面和 Agent 调用同一套创建、查询、修改、完成、归档和撤销接口。Agent 操作自己内置的工具直接使用这些接口，无需截屏点击自己的日历。

最小对象：原始输入 `capture`、媒体 `asset`、日程 `calendar_event`、清单/条目 `list/list_item`、笔记 `note`，关联已有 `goal` 与执行记录。共同字段包括归属、稳定 ID、版本、原始来源、创建/修改者、时间及删除状态。实体字段因类型不同保持清楚，不把所有东西塞成一条聊天消息。

| 同步情况 | 用户应看到的行为 |
| --- | --- |
| 手机创建，电脑在线 | 同一个 ID 的内容出现在电脑；后续编辑、附件和完成状态同步 |
| 两端离线修改同一条 | 保留双方修改；安全合并不同字段，同一时间字段冲突保留选择，不静默覆盖 |
| AI 整理还没结束，用户已修改原记录 | AI 只能提交基于原版本的建议；版本过期需重读，不覆盖用户新内容 |
| 上传被中断或重复提交 | 原内容仍在本机，恢复后续传/重试；幂等键保证只创建一份结果 |
| 一端删除，另一端正在同步 | 删除版本传播；迟到的识别结果不能复活记录，也不能继续产生提醒 |
| 修改或完成待办 | 老提醒失效，所有端重开后是同一状态；不残留旧通知继续打扰 |

在线即时分发更新、断线后按版本补齐。界面区分“本机已保存、正在同步、已同步、需处理冲突”，不承诺断网时其他设备也已拿到新内容。多端一致指同一内容、状态与归属，不要求每个平台使用同样的控件布局。

提醒由一条中心提醒记录派发，原生端负责展示与交互；用户在一端处理后，其他端同步已处理状态。应用内消息是持久事实，推送不是数据库。原生系统日历的提醒与 Wearing 自有提醒要有清楚的负责方，避免同一件事双重响铃。

## 6. 内置工具与 iOS 原生能力共同工作

内置日历始终可用；连接系统日历后，指定 Wearing 日历/映射范围进行同步。每条外部事件保留来源账户、原事件 ID、版本及镜像关系，多个 Apple 设备看到同一个 iCloud 日程时不创建多个副本。用户在任一端修改后走同一冲突处理流程。

| 原生能力 | 首批动作与体验 | 实现依据与边界 |
| --- | --- | --- |
| 日历、提醒事项 | 在 Wearing 创建后写入用户选定日历/清单；也读取原生端修改 | EventKit 支持创建/读写。系统事件的只写权限不能读回；读取事件需完整权限，不能把产品内只读模式描述为系统只读授权 |
| Siri、快捷指令、桌面小组件 | “记一句”“添加日程”“查看今天”“完成事项”，直达同一份记录 | 用 App Intents 暴露 Wearing 自己的动作；不等于可任意操作所有第三方 App |
| 相机、照片选取 | 拍摄与语音备注组合；从图库选图后整理 | 使用原生相机和系统照片选取器；选图不需要先取得全部图库内容 |
| 系统分享 | 把网页、照片、文件送入 Wearing，可补一句语音/文字用途 | iOS Share Extension / Android 接收分享；扩展只做可靠接收与提交，重处理交给云端 |
| 通知、地图、搜索 | 从通知完成/延期；从地址打开地图；按已允许范围搜索 Wearing 内容 | 按系统允许的功能接入，并为旧系统保留 App 内入口 |

官方依据：[EventKit 权限与读写](https://developer.apple.com/documentation/eventkit/accessing-the-event-store)、[App Intents](https://developer.apple.com/documentation/appintents/creating-your-first-app-intent)、[PhotosUI](https://developer.apple.com/documentation/photosui)、[iOS 分享扩展](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html)、[Android 接收分享](https://developer.android.com/develop/ui/compose/sharing/receive)。这些是可采用的系统机制，本轮未完成 Wearing 的原生实现。

Wearing 备忘首版由自己的笔记对象承担；Apple 备忘录先通过系统分享/用户选择的内容进入，后续按实际开放能力验证快捷指令适配，不预先承诺全量数据库双向同步。既有 EventKit 授权不代表取得 Apple 备忘录权限。

## 7. 整合路线与首版验收

桌面日历先评估 [FullCalendar 的现成视图与拖动能力](https://fullcalendar.io/docs)，标准插件有 [MIT 许可](https://fullcalendar.io/license)，按项目保留声明，不混用需另行许可的 Premium。笔记编辑先评估 [Tiptap](https://tiptap.dev/docs/editor/getting-started/overview) 的现有编辑能力；语音转写/识图使用成熟模型服务。FullCalendar 标准组件已整合；Tiptap 仍为候选，未购买 Premium。OCR 与语音转写采用 Apple Vision / faster-whisper，不自行开发日历排版、富文本编辑引擎或语音识别模型。

首个可用版本同时包含：自有日历创建与编辑、清单、短笔记、附件来源、文字/语音整理、稳定记录 ID 与多端同步。相机原生界面先在手机验证包测试；桌面和网页先能接收用户选择的图片。自有日历写入不等待第三方 OAuth 或已有日程。

随后接 Mac / iOS 日历与提醒事项读写，再扩展其他日历来源。移动端捕获、原生分享与断网保存从第一轮原型进入设计；不等桌面完全结束后才考虑。

验收先从下面五件简单事情开始：

1. **从零创建**：全新账户、未连任何外部日历；一句话建成日程，电脑和手机出现同一条，提醒设置可见，可编辑和撤销。
2. **照片配语音**：拍一张活动海报，补充“周六想去，先收藏”；生成带原图的笔记和候选日期，不误建确定行程。再说“安排进去”更新关联原记录。
3. **清单即用**：说“加洗衣液和纸巾”；手机勾掉纸巾后桌面也完成；重复消息不重复新增。
4. **原生往返**：在 Wearing 建一条授权同步的日程，在 Apple 日历改时间；所有 Wearing 端显示新时间且只有一条；提醒只按最新安排触发。
5. **离线与竞态**：断网拍照退出 App，回来原件不丢；电脑修改与迟到 AI 结果冲突时保留人工修改；记录删除后不会被后台整理复活。

衡量首次真实保存所需操作、捕获成功/丢失、整理纠正率、重复/冲突数、提醒是否有帮助、再次自发记录；不把用户填了多少日程当作产品价值。

下一步原型采用“手机拍/说 → 内置日历或笔记 → 桌面直接编辑 → Wearing 根据变化继续推进”，以同一组内容验证各端，而不分别画互不相关的客户端。
