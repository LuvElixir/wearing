# Wearing：请从整体上重新梳理这个 Personal Agent 整合探索项目

这是我和 Codex 最近讨论后的完整同步，以本条为最新方向。请认真研究、独立判断，帮助我们一起梳理。先理解整个探索命题，再研究方案组合；不要仅根据下面列出的候选直接认可选型。涉及现有项目能力、服务资格和价格，请查看官方文档或源码，标明事实、推断和待实测项。当前日期为 2026-10-01。

## 1. 我究竟想做什么

项目名已定为 Wearing。它是“属于我的行动者，同时也是延伸出去的另一个我”。名字来自让 Agent 穿上人的目标、偏好、判断、账号和权限，出去行动的叙事。VI 已选钴蓝卷袖角色，标志还要进一步简化，本轮重点回到整体项目规划。

我的最新原话是：“我们这个极客项目，就是要探索 agent 的能力边界。我们尝试把人类在社会上所需要的一切通过各种方式让 agent 能够拥有和使用。”

我们做的是各种优秀方案的整合。我没有期待自己把通用 Agent 技术做得比 Hermes 等成熟项目更好。我们要亲自把真实流程里的细枝末节走通：人如何得到一台电脑、一个手机、邮箱、电话号码、支付工具、业务账号、持续的工作环境与社会联系，再怎样让 Agent 获得并使用这些能力。

“整合”不仅是拼 API 或调用工具，也包括资源从哪里获得、适用条件、开通材料、配置、人工步骤、成本、真实任务验收、长期维护、失效恢复与迁移。自己走通后，把稳定步骤做成自动检测、脚本、连接器、安装引导和维护工具，让后面的人更快复现。未来甚至可以运营小机房，提供托管电脑和手机，但现在首先是极客探索项目，不要按商业 SaaS 的增长或多租户需求提前扩大建设。

## 2. 接入手段的态度

我不寄希望于每个网站/App 提供 API 或 Agent 接口。完全接受 Computer Use、浏览器自动化、Open-AutoGLM 手机视觉控制、真实设备、远程桌面、必要时特定设备 Root 等方案。API 可用且可靠时可以用，但“没有 API”不是放弃某项能力的理由。这里说的是业务服务接口，不是在拒绝模型 API。

请认真把图形界面控制作为实际执行路线来设计，并比较其成功率、延迟、费用、维护成本和人工接管体验。也不要反过来把所有任务都强制变成截图点击。钱该省就省，能显著提高成功率的成熟方案、模型和服务可以花钱，评估的是完成真实任务的总成本。

“Agent 拥有”在这里首先指长期、稳定、被授权地控制和使用资源。请具体区分用户自带、专门给 Agent 配置、第三方托管，以及真正涉及自然人/公司资格的账户归属。技术可操作性、申请资格、平台可用性、本人必须完成的环节分别说明。

## 3. 当前条件与已对齐的行为

- 我有闲置 MacBook Air，具体芯片/系统待检测，可作为首个验证资源，不代表产品必须绑定 Mac。
- 我希望执行电脑优先研究 Mac 或 Windows，担心某些网站对机房环境的接受程度；这是待验证问题，不能把操作系统直接等同于网络位置、账号资格或风控结果。控制服务运行在哪里和浏览器实际在哪里操作可分开。
- 手机按不能插实体 SIM 处理。eSIM 是否可用未确认。手机 App 控制和电话/短信号码服务分开解决，也研究云手机和托管真机。
- 目前没有已确认可用的海外手机号、海外银行卡/U 卡，也没有境外居留。资源方案必须从中国大陆用户的真实条件出发验证。
- 所有设备和服务都应有可替换的连接方式：本地、远程、自带、租用、未来自营均可，但能力差异要诚实呈现。
- 希望平时不用自己进电脑操作；必须保留远程接管和故障恢复。
- 主动做事来自对话、灵感、业务事件和既有目标。随口一个想法，先做预算有限的初步研究，再反馈；不假设硬件全天录音。
- 长期经营由我决定方向，Agent 日常推进；投资按用户确定的策略执行。
- 目前仍处于规划和研究阶段，没有跑通真实资源开通及端到端业务。

## 4. 用来检验能力的实际目标

帮助订阅 ChatGPT/Claude 等服务；开设和管理海外网店；投放及管理 Google 广告；在账户和权限条件成立时按用户策略执行股票或加密货币任务；从日常上下文产生有限研究并返回结果。

这些是验收场景，不应把整个项目缩成其中一种垂直产品。它们会暴露邮箱、号码、支付、账号、电脑与手机之间的真实依赖。请同时保留完整能力地图和分批验证顺序。

## 5. 底座候选：OpenAgentCore 与 Hermes

请重点研究：
- https://github.com/MiniMax-AI/OpenAgentCore
- https://github.com/NousResearch/hermes-agent
- OpenClaw 作为另一个成熟整合参考，不预设必须并入。

我提出的候选是：“MiniMax 的 OpenAgentCore 是否适合作为 personal agent 底座，然后接入 Hermes？”这是待判断的架构问题，并未决定采用。

Codex 已检查 OpenAgentCore 的 main 提交 13f6550399f988b742907d3839a98e1a4991b0aa。检查时最新稳定发布为 v0.0.2；main 能力与 release 要分开。以下是源码/文档初查，不是真机验证：
- Core 管 API、会话、持久状态与执行管理；Runtime 连接机器；原生引擎负责模型和工具循环。
- 内置 Codex、Claude Code、MiniMax Code，注册代码没有 Hermes。接 Hermes 要实现适配器的配置、执行、取消、回执、恢复和验收，不能说“支持 MCP 所以直接能接”。
- 有用户电脑安装接入、Skills/Plugins/MCP、文件产物与 Docker/E2B/microsandbox 计算环境路线。
- 原生安装矩阵列 macOS arm64、Linux amd64、Windows amd64；Windows 不支持 MiniMax Code。官方 Core 一键部署走 Linux amd64 + Docker Compose + PostgreSQL。
- 自带电脑接入围绕 Session/Environment，每会话独立安装目录/凭据。长期“我的设备”、跨任务复用、占用协调、接管与救援仍需验证/补充。
- Runtime 使用启动账号权限，本身不提供操作系统隔离。没有现成的手机/号码/支付开通闭环。
- 公共能力有组合限制：子 Agent 与 functions/HTTP MCP 组合拒绝；Claude/MiniMax 的公共 token usage 是 null。具体以所选版本矩阵为准。
- example/parsar 有单用户工作台和连接机器 UI，可参考，但不是现成的 Wearing。
- Codex 只运行了 1 项合成安装包目录测试并通过；没有启动 Core、连接闲置 Mac 或调用真实模型。上游自带机器实模型验收文档主要对应 Linux，不能据此承诺 Mac 全部可用。

请独立核对这些判断，比较：A. Hermes 直接做核心并整合设备工具；B. OpenAgentCore 管执行环境，Hermes 做原生引擎适配；C. 使用 OpenAgentCore 现成引擎，暂不接 Hermes；D. 若有更合适的简单组合请提出。指出重叠职责、维护负担、值得复用与不值得自建之处。
